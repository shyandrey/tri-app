## Interpretation / recommendation

Morgan has TWO new starts: Nice MEN #23, tier S (weight 1.20, no podium bonus), SOF 96.35 → factor 1.0635; Riviera DNF, tier A (weight 1.10), SOF 96.12 → factor 1.0612. Nice contributes `100 / 23^0.65 * 1.20 * 1.0635 * 0.9877321543 = 16.4223324156` to numerator and 0.9877321543 to denominator. DNF contributes zero to numerator and 0.9933754231 to denominator. This is intentional existing DNF semantics.

Before: `292.8632782986 / 5.2692959332 = 55.5792048898` performance; `* 0.92 * 1.08 = 55.2234979785` score. After: `309.2856107142 / 7.2504035106 = 42.6577100518`; `* 0.955 * 1.0975 = 44.7100791267`. More starts increase confidence/bonus, but do not compensate the lower weighted mean. No result or ranking correction is needed.

Production App.tsx captures `rankingAsOf = new Date()` once at module evaluation; it is not a live ticking or per-render ranking clock. Both ranking functions receive the same captured timestamp. Utilities independently default to new Date() when callers omit it. A fresh browser load uses that browser's system clock; a static Vite build does not freeze the timestamp. An already open page does not re-evaluate ranking at midnight.

With unchanged eligible starts and no future results becoming eligible, every recency weight gets the SAME factor `2^(-deltaDays/730)` as time advances. It cancels from numerator/denominator. Starts-based confidence and bonus do not decay. Consequently this formula does not lower an inactive athlete's absolute score just because days pass; recency changes relative weighting of old vs new performances when results are added. Changing that property would be a separate ranking-formula task.

Recommendation: a single dataset-derived asOf, at 12:00 UTC on the latest represented completed edition date, reused by ranking sort, ranking rows and country strength. Latest in the present dataset is French Riviera 2026-09-19. Exclude scheduled editions without results. Result import must reject future/uncompleted editions (or explicitly record a verified completion state); otherwise using max date blindly could advance the clock incorrectly. Prefer enforcing completed-only data at import to consulting each browser's current clock: the latter would retain device-clock dependence. Handle an empty result dataset explicitly (empty rankings, no invented timestamp). Same-day multiple editions share the clock.

This gives deterministic browser/SSR/tests across machines and stable values between imports. Tests can pin a fixture dataset or explicit asOf. Future automated imports should validate date/completion, source provenance, identities, metadata and audits before versioning; incomplete in-progress results should not advance the clock. No production clock implementation was changed in this task.
