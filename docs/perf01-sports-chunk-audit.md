## Executive assessment

The warning is real: `sports-entry-BmJxP9qc.js` is **1,295,176 bytes minified**, but only **263,224 bytes gzip** with Node's default compression; measured local Vite transfer including protocol overhead is263,800B. A large minified file is not itself evidence of unacceptable execution time.

The cause is a coarse lazy boundary, not showcase image embedding or a heavy third-party sports library. All sports pages, full athlete/results registries, enrichment provenance and official standings evidence are bundled together. First navigation to Rankings also links all results and calculates the internal athlete ranking, although official standings do not use that ranking.

On a local Chromium mobile-sized run with CPU4× slowdown,150ms latency and1.6Mbps download, median Home→Rankings readiness is3,195ms; its script-time delta is76.4ms and observed long-task excess over50ms is3ms. Repeated Rankings navigation is19ms with zero new JS transfer. This points to first-use delivery as the stronger concern under these conditions, not sustained main-thread blocking. These are route-DOM readiness measurements, not fully decoded artwork, LCP, INP or real iPhone performance.

**Recommendation:** separately authorize a focused prototype that isolates Rankings from the full sports data/ranking initialization and generates deterministic runtime projections from retained evidence registries. Measure before committing to wider race-data partitioning. Do not raise the warning threshold as a substitute for optimization.

**Release assessment:** no demonstrated functional blocker or sustained CPU failure in this audit. Treat cold-route latency as an open P1 performance risk requiring owner acceptance and physical Safari/Telegram checks before release. No approved latency SLO was supplied, so this report cannot declare a universal performance PASS or make optimization unconditionally release-blocking. PERF-01 is not closed.
